4b. **AC coverage matrix — cite code AND test for every acceptance criterion.** For each in-scope AC, locate the specific code file/line range that implements the behavior AND the specific test file/method that verifies it. This is a stricter check than the PASS/FAIL above: an AC can be "PASS" on paper (behavior seems present) yet fail the matrix if either the code or the test cannot be pinpointed. A PASS without citations is not a PASS — it is an untested claim. Rules:
   - **Code must be citable to file + line range.** "Handler somewhere" does not count; `src/Foo/BarHandler.cs:34-52` counts.
   - **Test must be citable to file + method name.** "Tests cover this" does not count; `tests/BarTests.cs:ShouldFooWhenBar` counts.
   - **Integration test citations beat unit test citations** when the AC describes end-to-end behavior; unit test citations beat integration test citations when the AC describes pure domain logic. Cite the tier that actually catches the bug the AC is protecting against.
   - **An AC with code but no test = test gap.** Real defect — the behavior exists but a regression would ship silently.
   - **An AC with test but no code = spec gap OR dead test.** Investigate: is the test asserting on something that isn't actually built, or is the AC satisfied by framework behavior (e.g. framework returns 401 automatically) that has no dedicated code?
   - **An AC with neither = not implemented.** The PASS/FAIL above should have caught this; the matrix is the second net.

7. **Exception handling review.** Walk every `catch` block, global exception handler, middleware, and framework exception filter in the changed code. For each, verify:
   - **Client errors surface as 4xx, not 5xx.** Exceptions that represent bad input from the caller (`BadHttpRequestException`, `JsonException` from body deserialization, `ArgumentException` on request parameters, model-binding failures, validation exceptions) must produce a 4xx response — typically 400 for malformed input, 401 for auth, 403 for role, 404 for not-found, 409 for conflict. A global handler that catches these and returns 500 is a real defect: it misclassifies a caller mistake as a server bug, misleads observability, and pollutes on-call alerts.
   - **Cancellation is distinguished from server errors.** `OperationCanceledException` / `TaskCanceledException` triggered by client disconnect or request timeout is NOT a 500 — it is either 499 (nginx convention) or a silent close, and MUST NOT be retried by any retry policy (Polly, EF Core execution strategies, etc.).
   - **Transient vs permanent persistence failures are distinguished.** A generic `DbUpdateException` catch that treats every DB failure as transient will retry constraint violations (PK, FK, CHECK, NOT NULL) — which cannot succeed on retry — and mask them as timeouts. Verify the code classifies by SQL error number (or equivalent for the DB engine) and only retries genuinely transient failures.
   - **Unhandled exceptions have a documented catch-all.** There should be exactly one final catch-all (global exception handler / middleware) that returns 500 with a support-actionable payload (correlation id, batch/request id). Multiple overlapping catch-alls are a smell.
   - **No exception is swallowed silently.** A `catch { }` with no logging is a defect unless the enclosing method's contract explicitly documents it (e.g. `TryGet…` patterns).
   For each finding, cite the file / line and the specific exception type + wrong status code.
