6b. **Declared-vs-used audit — every declared dependency, tool, and config value must have a real call site.** Walk the following surfaces in the target repo and verify each declaration is actually referenced by production or test code. Declarations that no code reads are dead weight — worse when documentation cites them as active, because then the drift becomes a lie the reader has to unravel.
   - **NuGet / npm / pip / gem packages** (`.csproj`, `Directory.Packages.props`, `package.json`, `requirements.txt`, `Gemfile`, etc.): for each declared package, grep for at least one non-trivial import / `using` / `require` / call site. A package with zero references is dead. A package referenced only by a using directive that has no method call, class instantiation, or generic parameter is also dead — it satisfies the compiler but nothing more.
   - **Config keys** (`appsettings.json`, environment-variable declarations, `.env` templates, cloud config): for each declared key, verify at least one binding (`GetSection`, `Get<T>`, `Configuration["Key"]`, options pattern, direct env-var read). A config key nothing reads is a promise the code does not keep.
   - **CLI tools / build-time dependencies** (dotnet-tools.json, package.json scripts, Makefile targets, CI workflow steps): each tool should be invoked somewhere in the build, test, deploy, or dev-loop path. Declared-and-uninvoked = documentation for a workflow the team doesn't actually run.
   - **Docs claims about tools** (README, ADRs, architecture.md, verification reports): whenever a doc names a specific tool / library / framework / DB provider as part of the stack, cross-check that the corresponding surface above actually contains it AND that surface has call sites. The failure mode is: an ADR names SQLite as the unit-test DB, the csproj lists the SQLite package, but zero test code uses it — the whole triangle is drift.
   For each finding, cite the declaration location AND the fact of zero call sites (with a representative grep pattern the reviewer can re-run). Distinguish three severities: **dead** (declared, unused, undocumented — remove), **drift** (declared, unused, but docs claim it's active — remove the declaration OR update the docs), **suspect** (declared, has a using directive but no call — investigate whether it's transitively required or actually unnecessary).
7. **Exception handling review.** Walk every `catch` block, global exception handler, middleware, and framework exception filter in the changed code. For each, verify:
   - **Client errors surface as 4xx, not 5xx.** Exceptions that represent bad input from the caller (`BadHttpRequestException`, `JsonException` from body deserialization, `ArgumentException` on request parameters, model-binding failures, validation exceptions) must produce a 4xx response — typically 400 for malformed input, 401 for auth, 403 for role, 404 for not-found, 409 for conflict. A global handler that catches these and returns 500 is a real defect: it misclassifies a caller mistake as a server bug, misleads observability, and pollutes on-call alerts.
   - **Cancellation is distinguished from server errors.** `OperationCanceledException` / `TaskCanceledException` triggered by client disconnect or request timeout is NOT a 500 — it is either 499 (nginx convention) or a silent close, and MUST NOT be retried by any retry policy (Polly, EF Core execution strategies, etc.).
   - **Transient vs permanent persistence failures are distinguished.** A generic `DbUpdateException` catch that treats every DB failure as transient will retry constraint violations (PK, FK, CHECK, NOT NULL) — which cannot succeed on retry — and mask them as timeouts. Verify the code classifies by SQL error number (or equivalent for the DB engine) and only retries genuinely transient failures.
   - **Unhandled exceptions have a documented catch-all.** There should be exactly one final catch-all (global exception handler / middleware) that returns 500 with a support-actionable payload (correlation id, batch/request id). Multiple overlapping catch-alls are a smell.
   - **No exception is swallowed silently.** A `catch { }` with no logging is a defect unless the enclosing method's contract explicitly documents it (e.g. `TryGet…` patterns).
   For each finding, cite the file / line and the specific exception type + wrong status code.
